# 按条记录同步与同步服务设计

日期：2026-10-11
分支：`feature/record-sync`

## 1. 背景

现有云同步把数据存为对象存储（S3/R2、WebDAV）中的文件：浏览历史与阅读进度走 op 包加快照（format v2），其余 11 种类型每次整份上传、下载、合并（`latest.json`）。已在代码中确认的问题：

- 代码中没有删除标记。收藏按画廊编号取并集，一台设备取消的收藏，下次同步会被远端带回；浏览历史的删除同样不能传播。
- 每种类型各有一个合并函数（`sync_merger.dart`），新增类型就要新写一套；旧客户端遇到未知类型码会清除远端数据（2026-10-04 实证）。
- 对象存储无法回答"某个时刻之后有哪些变化"，落后的设备只能列举后逐个下载（2026-10-11 macOS 设备一次要下载 248 个包）；也没有条件写入，快照与压实只能靠约定避免互相覆盖。

## 2. 目标与范围

1. 新增同步方式"同步服务"：客户端按条记录与一个 HTTP 服务交换数据，服务端按序号返回增量。参考实现是仓库 `sync_server/` 中的 Cloudflare Worker 加 D1 数据库，用户自行部署。
2. 13 种同步类型统一为同一种记录，合并规则只有一条，删除可以传播，未知类型原样保存。
3. 现有的 S3/R2、WebDAV 同步保持不变，作为默认方式继续提供。两种方式并行一段时间：新方式先在自愿使用的设备上验证，之后再决定是否把对象存储也迁移到记录模型。

不在本次范围：对象存储的记录化格式（v3）、历史版本（同步服务不提供 `latest.json` 的版本列表与恢复）。

## 3. 记录模型

每条记录有以下字段：

| 字段 | 含义 |
|---|---|
| `kind` | 类型名，字符串 |
| `key` | 类型内的键 |
| `value` | 内容，JSON 字符串；删除时为 null |
| `updatedAt` | 修改时间，`SyncTimeUtil` 的固定宽度 UTC 格式（字典序等于时间顺序） |
| `device` | 写下这一版本的设备编号（沿用 `syncDeviceId`） |
| `deleted` | 是否为删除标记 |

**合并规则**：同一 `(kind, key)` 以 `(updatedAt, device)` 字典序较大者为准。`device` 只在时间完全相同时决定胜负，保证各端结果一致。删除是一条 `deleted = true` 的记录，同样参与比较，因此可以传播；之后在任一设备上重新添加，新记录的时间更晚，又会恢复。删除标记永久保留（每条几十字节）。

### 3.1 各类型的记录

| kind | key | value | 本机时间来源 |
|---|---|---|---|
| `history` | 画廊 gid | `jsonBody` | 行的 `lastReadTime` |
| `readProgress` | `subConfigKey` | 进度值 | 行的 `utime` |
| `nhentaiFavorite` / `wnacgFavorite` / `jmFavorite` | 画廊 gid | 收藏条目 JSON | 首次：`favoritedTime`；之后：配置行 `utime` |
| `quickSearch` | 名称 | `{"order": 位置, "config": 搜索配置}` | 配置行 `utime` |
| `searchHistory` | 关键词 | 关键词 | 配置行 `utime`（见 3.3） |
| `blockRules` | `groupId` | 该组规则列表（不含本机自增 id） | 发现变化的时刻 |
| `syncSetting` / `komgaSetting` / `nhentaiApiSetting` / `eh2telegraphSetting` / `jmAccount` | `default` | 整份配置字符串 | 配置行 `utime` |

### 3.2 本机副本

本机新增一张表 `sync_record`，是本机所知的全部记录（含其他设备写入的、本机不认识的类型）。除上表字段外还有：

- `dirty`：本机改动，尚未推送成功。
- `applyPending`：来自服务端、胜出但尚未写入应用数据。
- `localHash`：上次与应用数据对齐时，本机导出内容的散列。只用于小类型判断"应用数据是否在此之后改动过"。

应用数据（收藏、快捷搜索等各自的存储）是副本的物化结果；副本与应用数据之间由每种类型的适配器转换。

### 3.3 发现本机改动

- **浏览历史与阅读进度**：沿用 `PendingSyncTracker` 的待推送集合（写入路径已经标记）。删除浏览历史时（单条或全部），在副本中直接写入删除标记。首次使用同步服务时，把全部行写入副本。
- **其余类型**：同步开始时导出应用数据，与副本比较：
  - 键在本机存在、导出内容的散列与 `localHash` 不同：本机改动过，写入新版本。时间取本机时间来源，并且不早于副本中该记录的时间加 1 微秒——本机的修改发生在看到副本那一版之后，不能因为别的设备时钟偏快而输掉。若该记录正等待物化（`applyPending`），说明本机修改时并没有看到它，此时只按时间比较、不加 1 微秒。
  - 键在副本中存在、曾与本机对齐过（`localHash` 非空），本机已没有：本机删除了它，写入删除标记。
  - 某类型第一次处理时（副本中没有对齐记录），只增加、不删除：本机条目与副本条目按时间比较，本机较新才写入。
- **搜索历史的顺序**：本机列表按新旧排列。从最旧往最新检查，若某个关键词在副本中的时间不晚于排在它后面的关键词，就说明它被重新搜索、移到了前面，把它的时间提到配置行的 `utime`。这样重新搜索一个已有关键词只产生一条记录。

### 3.4 物化

- 小类型：先再发现一次本机改动（把同步期间的本机修改并入副本），再用该类型全部未删除的记录重建应用数据并刷新对应服务，随后重新导出，更新每个键的 `localHash`。
- 浏览历史与阅读进度：只处理胜出的键。写入用现有的带时间条件的写入（`batchRecordIfNewer`、`batchWriteIfNewer`）；删除只删除时间不晚于删除标记的行。

## 4. 同步过程

一次同步依次执行：

1. `GET /v1/info` 取得服务端数据库编号。与本机记录的编号不同（第一次使用、换了数据库或数据库被重建），则游标归零，副本中全部记录标为待推送。
2. 发现本机改动（3.3），只处理此前已处理过的类型。
3. 拉取：从游标开始分页拉取其他设备写入的记录，按合并规则写入副本；胜出的标为待物化。每页处理完立即保存游标，中断后从断点继续。
4. 第一次处理的类型在拉取之后才发现本机改动，与服务端已有的记录比较。这样，一台已经通过对象存储同步过、数据与服务端相同的设备，第一次使用同步服务时不会把相同的内容再推送一遍。
5. 物化所有待物化的记录（3.4）。
6. 推送：把待推送的记录分批推送；成功后只清除推送期间未再修改的记录的标记。

从同步服务换回对象存储时，下一次对象存储同步会把浏览历史与阅读进度完整推送一次（重置 `oplogFullPushDone`）；反过来，每次对象存储同步后，下一次使用同步服务时会重新完整读取这两种数据（待推送集合已被对象存储消耗）。

本机不认识的类型只存入副本，不物化；升级到认识它的版本后，该类型第一次处理时会物化副本中已有的记录。

`SyncService.sync` 的单飞、总时限、读进度排队等机制不变；`currentProvider == 'server'` 时由新引擎执行，否则仍走原来的对象存储路径。

## 5. 服务端接口（协议 1）

所有请求带 `Authorization: Bearer <令牌>`；令牌不符返回 401。

- `GET /v1/info` → `{"protocol": 1, "database": "<数据库编号>", "seq": <当前最大序号>}`
- `POST /v1/push`，请求体为记录数组（每条含 `kind`、`key`、`value`、`updatedAt`、`device`、`deleted`）→ `{"received": <条数>}`。服务端在一条语句中逐条按合并规则写入，每条写入获得一个新的递增序号。
- `GET /v1/pull?since=<序号>&device=<设备>&limit=<条数>` → `{"records": [...], "next": <下次的游标>, "more": <是否还有>}`。只返回其他设备写入的记录；`limit` 上限 500。

### 5.1 Cloudflare Worker + D1 参考实现

D1 免费额度下的限制决定了实现方式：每次请求最多 50 条查询、每条查询最多 100 个绑定参数、单个字符串最大 2 MB、Worker 每次请求 10 毫秒 CPU。因此：

- 推送把整个请求体作为一个参数交给 SQLite，用 `json_each` 展开，一条 `INSERT ... ON CONFLICT DO UPDATE ... WHERE` 完成全部写入与合并判断；Worker 不解析记录。
- 拉取用 `json_group_array` 在 SQLite 中拼好记录数组，Worker 只拼接响应文本。
- 序号取 `max(seq)` 加行号；D1 的写入是串行的，序号顺序就是提交顺序，按序号拉取不会漏读。
- 表结构由 Worker 在第一次请求时创建（`CREATE TABLE IF NOT EXISTS`），用户不需要执行建表语句。

客户端每次推送不超过 200 条、约 800 KB；拉取每页 200 条。

## 6. 设置与界面

- 同步设置新增 `syncServerUrl`、`syncServerToken`；同步方式下拉框新增"同步服务"。
- 选择同步服务时显示地址与令牌两个输入框，以及部署说明的提示；历史版本相关设置不显示。
- 连接测试调用 `/v1/info`。

## 7. 部署（用户侧）

`sync_server/README.md` 给出步骤：创建 D1 数据库，把 `wrangler.example.toml` 复制为 `wrangler.toml` 并填入数据库编号，用 `wrangler secret put SYNC_TOKEN` 设置令牌，`wrangler deploy`。令牌存为 Worker 的加密变量，不写入任何文件。

## 8. 测试

- `sync_server/test/`：在本地 D1 上测试鉴权、合并规则、序号分页、按设备过滤、数据库编号稳定。
- `test/record_sync_test.dart`：用内存中的服务端模拟，验证两台设备之间的首次合并、删除传播且不复活、数据相同的设备相遇后不再推送、同键冲突、删除后再次阅读的浏览历史保留、搜索历史顺序、未知类型保存、拉取中断后续传、换数据库后全量推送。
- `test/record_sync_server_e2e_test.dart`：启动本地 `wrangler dev`，用真实的 Worker 与 D1 跑两台设备的同步；本机没有安装 `sync_server` 的依赖时跳过。
